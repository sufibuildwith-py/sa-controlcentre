SA EMPLOYEE — ANDROID APPLICATION REDEVELOPMENT
Project: SA Command / SA Productions
Application: SA Employee
Platform: Android first, architecture kept iOS-compatible
Status: Mobile client redevelopment
Primary Goal: Replace the unstable SA Navigator mobile client with a polished, reliable, production-oriented employee application without discarding the working Navigator backend/gateway architecture.
Important: Existing SA Command production release artifacts under release/ must remain untouched during this redevelopment.

1. PURPOSE
The existing employee Navigator prototype proved several important concepts:
- physical Android installation works;
- employee/device pairing works;
- employee identity can be loaded;
- employee messages can reach the phone;
- duty state can reach the backend;
- Navigator Gateway architecture works;
- owner-side Navigator map works;
- desktop/gateway/backend integration exists.
However, the current mobile application is not reliable or polished enough for real employee deployment.
Observed problems include:
- navigation behaving inconsistently;
- invalid pairing codes / unclear pairing failures;
- connectivity depending too heavily on development ADB state;
- app restarts sometimes leading to a completely white screen;
- initialization failures leaving no recovery UI;
- development app occasionally losing connection to Metro;
- UI reporting Location sharing active without proving GPS tracking actually started;
- physical-phone location telemetry not yet completing the entire pipeline;
- background location not yet proven;
- keep-awake errors occurring during duty testing;
- weak offline/reconnection UX;
- basic visual design that does not match SA Command;
- insufficient screen structure;
- poor use of scrolling space;
- limited motion/microinteractions;
- weak loading/error/empty states;
- development/release behavior not sufficiently separated.
The redevelopment will solve these problems as one coordinated mobile V2 rather than continuing to patch the prototype screen-by-screen.

6. CORE EMPLOYEE JOBS
The rebuilt application has five primary responsibilities:
1. establish and persist employee/device identity;
2. show today's assigned work;
3. start/end duty and manage transparent duty-scoped location sharing;
4. receive operational communication from SA Productions;
5. remain usable and understandable through connectivity failures, restarts and background transitions.
Everything else is secondary.

15. RETRY POLICY
Retries must be bounded.
Example philosophy:
immediate request
      ↓ failure
small backoff
      ↓
retry
      ↓ failure
larger backoff
      ↓
queue/retry later
Do not create infinite tight retry loops.
Do not repeatedly hammer the gateway when offline.

33. LOCATION TASK STARTUP MUST BE INDEPENDENT OF KEEP-AWAKE
The previously observed:
Unable to activate keep awake
must not be capable of preventing location tracking.
Keep-awake is not a prerequisite for background GPS.
Therefore:
keep-awake
must either:
- be removed if unnecessary; or
- operate as best-effort UI behavior;
- have its errors caught;
- never abort Start Duty;
- never control the tracking state machine.
Do not chain:
await activateKeepAwake()
await startLocation()
such that failure of the first prevents the second.
34. LOCATION SAMPLING
Initial field-test target:
time interval:        ~20 seconds
distance interval:    ~20 metres
deferred/batch window ~30 seconds
These values should be configurable.
Do not hard-code them across multiple files.
Create one location policy/configuration object.
35. LOCATION POINT MODEL
Each point should contain only necessary information.
Conceptually:

Do not put exact GPS coordinates in ordinary application logs.
36. LOCAL LOCATION OUTBOX
Every collected point should first become durable enough to survive network failure.
Preferred flow:

    │
    ▼

    │
    ▼
SQLite outbox
    │
    ▼
sync worker
    │
    ▼
Gateway
    │
    ▼
ACK
    │
    ▼
delete acknowledged point
Do not rely on:

    ↓
fetch()
    ↓

37. LOCATION IDEMPOTENCY
Use:
sessionId + sequenceNo
or the equivalent existing gateway contract.
A retry must not create duplicate telemetry.
38. LOCATION BATCHES
Upload bounded batches.
Initial target:
max 25 points
oldest first
On acknowledgement:
delete acknowledged rows only
Never clear the entire queue merely because one request returned successfully.

40. END DUTY

41. RESTART RECOVERY
When Android restarts/recreates the application process:

[ Resume location ]
or safely resume according to the validated lifecycle.
42. FORCE-STOP REALITY
Do not claim impossible guarantees.
Expo's current documentation states that Android background location stops if the application is terminated, and vendor behavior can differ when an app is removed from recents. Expo documentation
SA Command must therefore use freshness rather than assuming that duty == active means the phone is live.

93. OPEN-SOURCE REUSE RULE
Before writing a substantial UI primitive or infrastructure utility:
1. check whether Expo/React Native already provides it;
2. check existing project dependencies;
3. check React Native Reusables;
4. check a mature compatible OSS implementation;
5. adapt Aceternity visual patterns where appropriate;
6. custom-build only what is SA-specific.
Open source should save engineering effort.
It must not introduce unnecessary dependency complexity.
